# 92 · 岗位检索（内置）

> 解决什么：把"有哪些岗位在招"从模糊印象变成一份可投的清单。
> **本能力已内置，使用者不需要再安装第二个岗位搜索 skill。**

---

## 〇、来源与说明（必读）

本模块内置自 `job-search-multiplatform` v1.0.1，做了三处删改：

| 保留 | 删改 |
|---|---|
| 平台矩阵、五级降级链、搜索引擎检索式、跨平台去重、输出结构、合规边界 | 去掉与求职决策无关的打招呼/投递自动化；把"每次必须覆盖全部平台"改为"按行业调权重"；补上抓不到时的产业代理指标路径（`05-city.md` 2.2.1） |

**依赖**：脚本需要 Python 3.10+ 与 `requests`、`beautifulsoup4`。**不装也能用**——方式 3（搜索引擎聚合）不需要任何依赖，绝大多数场景够用。

**如果使用者本地已装同名 skill**，两者会重复触发。保留其一即可，不必都装。

---

## 一、什么时候用

| 场景 | 用哪一步 |
|---|---|
| M5 给城市打分（维度 1 岗位数量） | 检索式 → 数"前 30 条中的公司数" |
| M3 验证岗位名是否真实存在 | 检索式 → 能搜出 10 条以上 JD 才算合格岗位名 |
| M6 找目标公司与投递清单 | 全流程（含去重与 JD 补全） |
| 用户直接说"帮我找岗位""这岗位在哪招" | 全流程 |

**不该用它做的事**：判断"这个岗位适不适合我"（那是 M3）、判断"该去哪个城市"（那是 M5）。检索只提供事实，不做判断。

---

## 二、三个必填参数（缺就追问，不猜）

| 参数 | 说明 | 示例 |
|---|---|---|
| 岗位关键词 | 用 JD 里的词，不用行业词 | `Java开发`、`软件测试`，不是"互联网" |
| 城市 | 可多选，或"不限/远程" | `南京`、`南京+成都` |
| 薪资下限（可选） | 月薪 K | `8K以上` |

**岗位关键词不合格的处理**：如果用户给的词搜不出 10 条真实 JD，说明这个词不是岗位名。回到 M3，用具体岗位名替换。

## 四、五级降级链（每个平台独立执行，一种失败立即换下一种）

```
方式1 CLI 工具（已装且已登录，结构化 JSON，最优）
  ↓ 失败 / 未装 / 未登录
方式2 HTTP 直接抓取（requests + BeautifulSoup）
  ↓ 失败（反爬 / 动态渲染 / 空结果）
方式3 搜索引擎 site: 聚合（最稳兜底，无需登录）
  ↓ 无结果
方式4 详情页抓取（补全 JD 原文）
  ↓ 动态页无法解析
方式5 人工提示（请用户登录后重试，不阻塞其他平台）
```

**方式 1 的两个 CLI**（有则用，无则跳到方式 2）：

```bash
# BOSS直聘（安装：uv tool install kabi-boss-cli）
boss status --json | jq -r '.authenticated'   # 先检查登录，不要假设
boss search "关键词" --city 南京 --salary 8-15K --json

# 猎聘
liepin-cli job search --job-name "关键词" --address "南京" --output json
```

**方式 2 的脚本**：

```bash
python scripts/scrape_platforms.py --platform liepin --keyword "Java开发" --city "南京" --pages 2
python scripts/scrape_platforms.py --platform zhaopin --keyword "Java开发" --city "南京" --pages 2
```

平台 URL 模板、城市代码对照表（猎聘 bj/sh/sz、智联 530/538/765、BOSS 气象码）见 `references/92a-platform-methods.md`。

## 五、方式 3：检索式（无需登录，直接可用）

```
site:zhipin.com {岗位} {城市} 招聘
site:liepin.com {岗位} {城市} 招聘
site:zhaopin.com {岗位} {城市} 招聘
site:lagou.com {岗位} {城市}
site:huibo.com {岗位} {城市} 招聘      # 仅西南
site:eleduck.com {岗位} 远程           # 仅远程
```

**规则**：

- 加时间过滤（默认近一周）——这是"只保留在招岗位"的关键手段
- 每平台 1–3 个 query，总搜索 ≤ 20 次，每 query 取前 5 条
- `site:` 无结果时去掉 `site:`，改用"平台名 + 岗位 + 城市"
- 小众岗位自动扩同义词（"前端开发" ↔ "web前端" ↔ "JavaScript开发"）
- 摘要里抽不到 title/company/link 的条目直接丢弃并计数

## 六、活跃优先与去重

**只保留在招岗位**：

1. 标题含「停止招聘 / 已暂停 / 已下线」直接剔除
2. 新鲜度：发布或更新在 2 周内；多平台同时出现（说明真在招）
3. 排序：活跃度 → 多平台在招 → 薪资明确度 → 匹配度
4. 薪资"面议"不剔除，排后并标注

**去重主键** = 规范化公司名 + 规范化岗位名 + 城市。命中则合并：追加平台链接、薪资取更新的一方、JD 取更完整的一方。

详细规则见 `references/92b-dedup-rules.md`；合并可用 `python scripts/dedup_merge.py --input merged.json --out final.json --format md`（纯标准库，无依赖）。

## 七、输出

```markdown
# 岗位清单 — {岗位} · {城市} · {日期}

## 汇总
覆盖平台：BOSS ✅ / 猎聘 ✅ / 智联 ⚠️(降级聚合)
去重前 N 条 → 去重后 M 条；活跃 X 条

## 速览表
| # | 岗位 | 公司 | 薪资 | 地点 | 活跃度 | 链接 |

## 岗位清单（每条附完整 JD，按活跃度排序）
### 1. {岗位} — {公司}
- 薪资 / 地点 / 经验 / 学历
- JD：完整原文（职责逐条 + 任职要求），不做摘要
- 链接：BOSS url ｜ 猎聘 url

## 数据来源说明
各平台用的方式、降级记录、抓取时间、JD 未补全的条目编号
```

**JD 必须是原文，不做压缩。** 列表页只有摘要时，必须进详情页补全；补不到就标「JD 需平台内查看」，并列出编号——**不编造 JD 内容**。

## 八、抓不到时怎么办

这是常态。按顺序降级：

| 情况 | 处理 |
|---|---|
| 平台反爬 / 需登录 | 走方式 3 搜索引擎聚合 |
| 方式 3 也无结果 | 改用产业代理指标排序（`05-city.md` 2.2.1），并标注「估算，未核」 |
| 完全拿不到 | 明确说「抓不到」，给检索式让用户自己跑，不编数字 |

**输出里必须区分**：`[检索·yyyy-mm·平台]` 是抓到的；`[推断]` 是估的；两者不能混写成一句话。

## 九、判停

| 信号 | 我这边怎么做 |
|---|---|
| 覆盖 3 个平台仍 0 条 | 换关键词（可能是岗位名不对），回 M3 |
| 抓到 50 条以上 | 停，按活跃度取前 20 条，不要无限扩 |
| 单平台连续失败 2 次 | 放弃该平台，记入降级说明，不重试第三次 |
| 用户只想要"大概行情" | 只跑方式 3，不跑全流程——省时间 |
| 检索耗时超 15 分钟 | 停，先交付已有结果 |

---

## 十、合规边界

- 不绕过验证码与登录墙；需要登录时请用户人工完成
- 不并行轰炸平台；遵守随机延迟（2–5 秒）
- 只采公开可索引信息，用于个人求职
- 不把用户简历与个人信息发到无关外部服务

---

## 十一、与其他模块的接口

| 模块 | 本模块提供什么 |
|---|---|
| M3 | 验证岗位名是否真实（≥10 条 JD 才算合格） |
| M5 | 数"前 30 条中的公司数"与"行政区频次"（求职半径） |
| M6 | 投递清单与目标公司池 |
| M7 | 岗位 JD 原文（面试出题依据） |
| M9 | 岗位职责原文（试用期 KPI 对齐依据） |

**一份检索结果可以被四个模块复用。** 抓到后落盘保存，不要每个模块重抓一遍。
